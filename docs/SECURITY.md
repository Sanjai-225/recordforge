# Security and trust boundaries

## Authorization

Supabase Auth stores and verifies passwords. The application resolves usernames server-side to opaque Auth email identities; it never persists custom password hashes. Server pages and routes validate the session and protected database profile. The database independently validates `auth.uid()`, enabled/retired state, current generation and ownership. Changing a URL, JWT user metadata, request participant ID or browser state cannot assign a role.

Every exposed public table has RLS. Participants can read permitted own records but cannot directly insert/update official data. Explicitly granted RPCs implement all mutations. SECURITY DEFINER functions fix search_path, schema-qualify objects and validate the caller; internal helpers/views are private. Anonymous clients only receive sanitized snapshots and the revision-only realtime signal. Table and function grants are checked in the SQL suite. New migrations must preserve deny-by-default function execution.

The service-role key lives only in server-only modules and trusted scripts. It bypasses RLS by design; its limited code paths are registration reservation/provisioning/finalization, username lookup and hashed rate limits. Normal commands use the user's session. Bootstrap is an offline privileged operation, not a public role-assignment endpoint.

## Integrity

Register number, Event ID, username and active submission sequence uniqueness are enforced in the database. A reservation serializes registration capacity/identity checks before Auth provisioning. Interrupted Auth provisioning can be reconciled by the same request UUID; orphan identities have no application permissions.

Deployment and verification timestamps are generated by PostgreSQL during participant transactions. Verification requires deployment. Row locking plus repeat-safe transitions prevent double counting; a stale participant retry cannot reapply a milestone revoked by an administrative correction. Record and event versions reject stale edits. The database deadline blocks actions even if a disconnected browser shows time remaining.

Administrative corrections require reasons and write old/new evidence. Resets use typed confirmation, an extra review step, current generation/version and request receipts. The reset transaction retires participants and archives records while preserving developers/configuration/audit. Application authorization denies retired sessions immediately; the optional provider ban script is additional cleanup.

## Web controls

- State-changing requests require JSON and the exact configured Origin; cross-site requests are rejected. Supabase SSR cookies carry sessions; server/API snapshots are no-store.
- Zod validation and database validation both restrict input. Parameterized RPCs and allowlisted sort/config keys avoid arbitrary SQL.
- React escapes text. Submitted links require HTTP(S), no embedded credentials; external links use safe target/rel attributes. The server does not fetch arbitrary submitted URLs.
- Request bodies are limited to 32 KiB by the application after decoding. Vercel additionally enforces its platform request limit; another host should enforce an ingress body-size limit before buffering.
- Identity and edge rate limits are database-backed; stored identifiers are HMACs. Vercel's trusted forwarding header is used only on Vercel; other hosts must provide their own trusted ingress limits.
- Response headers include CSP, HSTS, no-sniff, frame denial and restricted permissions. CSP permits inline Next.js bootstrapping and inline styles; it is not a nonce-only CSP. Custom Supabase domains require updating the connection allowlist.
- CSV cells beginning with spreadsheet formula characters are escaped. Evidence exports require developer authorization.
- User-facing errors are sanitized; logs contain safe error codes/correlation IDs without request bodies, passwords, tokens, cookies or service keys.

## Privacy and evidence

Public snapshots omit register numbers, Auth UUIDs, private custom fields and audit history. Developers explicitly choose public columns and custom fields. Audit/export data remains private to developers. Treat evidence downloads as participant data and use organizer-controlled access and retention.

Database owners/service-role holders can alter infrastructure-level state. Application audit restrictions do not provide cryptographic nonrepudiation. Backups, limited privileged account access and change control are part of the operator's responsibility. The application provides records rather than legal world-record certification.

## Outstanding security validation

Local SQL tests and browser checks pass as recorded in TEST_RESULTS.md. Managed Auth/JWT/Realtime integration and native concurrency remain unexecuted release gates. Complete staging validation and backup restoration before accepting real competition data. No independent penetration test is claimed. Participant self-service password reset and a centralized security incident UI are not included; credential recovery is organizer-assisted through supported Supabase administration.
